## Verdict: **GAPS_FOUND**

Three MUST_FIX gaps prevent W1 from being forced into a secure implementation. Without them, W1 could ship code that passes all 54 tests and still ship Lacuna 2 (session-ID-as-token-hash) and a transitive dependency lint failure. Five SHOULD_FIX items would harden the suite further but do not block W1.

The overall design intent (RFC 8725 + OWASP) is sound. The 54 tests cover the primary attack classes well: alg-confusion, signature tampering, claim oracles, format/header attacks, oversized payload DoS, single-flight JWKS, log redaction, and oracle leakage in 401 bodies. The gaps are all in the **session-construction** stage (between "JWT validates" and "Session lands in context"), not in the JWT validation itself.

## Findings

### MUST_FIX (block W1)

#### M1. **Session ID HMAC is asserted by NO test (Lacuna 2 not enforced)**

**Severity**: critical — defeats constraint #3 of the ticket.

**Where**: nothing across the 54 tests asserts that `session.id` matches `expectedHmacSessionId(secret: kSessionSecret, sub: kValidSubject, iat: <iat>)`.

**Evidence**: the helper `expectedHmacSessionId(...)` in `_bearer_test_helpers.dart:401-409` is defined but **never invoked anywhere in the test suite**. Tests #15, #20, #23, #24, #28, #44, #46 all reach the success path and have access to `result.session`, but none compares `result.session!.id` to the HMAC.

**Why this matters**: Lacuna 2 (per the ticket) is the explicit security concern that a naive implementation would do `session.id = sha256(token)`. If the access token leaks (logs, Sentry, browser dev tools) it then becomes a stable correlation key against PII. Constraint #3 mandates HMAC-SHA256 with `serverConfig.sessionSecret` over `sub:iat` (or `jti` if present).

**Risk if W1 ships without this test**: W1 implements `session.id = sha256(token)`, all 54 tests pass green, the security review depends entirely on W2 (`flutter-code-reviewer`) noticing it by reading the implementation. The whole point of fail-first TDD is that the tests force the property — this test is missing.

**Required test (description, not code — W0 to add)**:
- Build a valid JWT with known `sub` and `iat`. Call middleware. Assert:
  - `result.session!.id == expectedHmacSessionId(secret: kSessionSecret, sub: kValidSubject, iat: <iat>)`
- Determinism: build a second valid JWT with the SAME `sub` and `iat`. Assert both produce the same session id.
- Variability: build a third with DIFFERENT `sub`. Assert different session id.
- Negative: assert `result.session!.id != crypto.sha256.convert(utf8.encode(token)).toString()` (explicitly forbids the naive implementation).

#### M2. **`jti` claim usage is asserted by NO test**

**Severity**: critical — constraint #3 says "use `jti` if present, else HMAC of `sub:iat`". No test exercises the `jti` branch.

**Where**: builder default omits `jti`. No test in Groups A–H sets `jti`.

**Risk**: W1 could implement only the HMAC branch and ignore `jti` entirely. Or W1 could implement only the `jti` branch and break HMAC fallback. Either path leaves a hole.

**Required tests (W0 to add)**:
- Token with `jti: "abc-123"` → `result.session!.id == "abc-123"` (or whatever the deterministic mapping is — the ticket should pin this).
- Token with `jti: "abc-123"` AND `sub:iat` HMAC would be different value → confirm `jti` wins.
- Token without `jti` → HMAC branch confirmed (covered by M1's positive test).

#### M3. **`pointycastle` not in `dev_dependencies`**

**Severity**: build-block — `_bearer_test_helpers.dart:28` does `import 'package:pointycastle/export.dart' as pc;`. The package is currently transitive via `dart_jsonwebtoken` only. The `depend_on_referenced_packages` lint will flag it; W1 will fail `dart analyze`.

**Where**: `apps/social_care_bff/web/pubspec.yaml` — `dev_dependencies` lists `lints`, `test`, `custom_lint`, `acdg_lints`. No `pointycastle`.

**Fix**: W0 (or W1 immediately on entry) adds `pointycastle: ^4.0.0` to `dev_dependencies`. The helper already documents this (line 14-18), but it must be ACTUALLY in the file before W1 starts so the test file compiles.

**Note**: this is technically a setup-defect, not a test-coverage defect. Listing here as MUST_FIX because it is a hard pre-condition for W1 entry.

### SHOULD_FIX (do not block W1, but should be addressed before W2 ships GREEN)

#### S1. **Test #44 does not strictly exclude cookie context from Bearer-won requests**

**Where**: `bearer_auth_middleware_test.dart:553-554`:
```
expect(cookieSession?.roles ?? const <String>{},
    anyOf(equals(<String>{}), equals({'admin'})));
```

The `anyOf` lets the implementation install the cookie session in context as long as the bearer session has the right roles. If a downstream consumer (e.g., `auth_guard`, audit logger, role checker) reads `sessionContextKey` instead of `bearerSessionContextKey` by mistake, an attacker could send a stolen cookie + valid Bearer and get the cookie's roles applied for some checks while the Bearer's identity is logged.

**Why this is SHOULD_FIX, not MUST_FIX**: the C00 ticket scope is the middleware itself; downstream consumers (auth_guard) are tested separately. But the priority hand-off is the security-critical contract.

**Recommended hardening**: tighten Test #44 to require `cookieSession == null` when Bearer wins, OR add a separate test that runs the *full* pipeline (`bearer → session → auth_guard → handler`) and confirms `auth_guard` reads `bearerSessionContextKey` first. The latter is more robust.

#### S2. **Test #52 catches token-as-literal but not partial-token leaks**

**Where**: `bearer_auth_middleware_test.dart:658`:
```
expect(record.message, isNot(contains(token)), ...);
```

If the logger does `token.substring(0, 32)` + `'...redacted'`, the literal `token` is not present, but a 32-char prefix of the JWT (header + part of payload, which is base64-decodable) IS leaked.

**Recommended hardening**: also forbid any contiguous substring of `token` longer than 16 characters. Concretely:
- For `i` in 0..token.length-16: `expect(record.message, isNot(contains(token.substring(i, i+16))))`.

This forces redaction to use a non-prefix marker like `[REDACTED]` rather than truncation.

#### S3. **Bearer-derived `Session` shape is asserted only partially**

The Session constructed from a valid Bearer must satisfy (per ticket §"Escopo de implementação"):
- `id`: HMAC (covered by M1 once added)
- `accessToken`: the JWT raw (NOT asserted anywhere — the only place is Test #44 implicitly, via roles-from-bearer)
- `refreshToken`: `""` (NOT asserted — W1 could set it to anything)
- `userId`: claim `sub` (asserted in Test #44 line 543 only)
- `roles`: parsed roles (asserted in Test #44 only)
- `expiresAt`: claim `exp` (NOT asserted — W1 could use Server's `sessionTtl` instead, breaking the contract)
- `displayName`: `null` (NOT asserted)

**Risk**: if W1 sets `session.expiresAt = clock() + Duration(hours: 1)` (the cookie-path default) instead of `DateTime.fromMillisecondsSinceEpoch(exp * 1000)`, the Bearer session's lifetime decouples from the JWT's `exp`. A token that's 30 minutes from expiring would be honored for 1 hour by the BFF.

**Recommended hardening**: add a test that takes a valid JWT with a known `exp` and asserts:
- `result.session!.accessToken == <the JWT raw>`
- `result.session!.refreshToken == ''`
- `result.session!.expiresAt == DateTime.fromMillisecondsSinceEpoch(exp * 1000, isUtc: true)`
- `result.session!.displayName == null`

#### S4. **No `kid` traversal / injection test**

Per constraint #4, `kid` is untrusted input and must be used only for `Map<String, RsaKey>` lookup — no path interpolation, no string concatenation into URLs or filenames.

**Where**: Test #35 uses a benign string (`'unknown-kid'`). No test exercises:
- `kid: '../../../etc/passwd'`
- `kid: '\x00admin'` (null-byte injection)
- `kid: '"; DROP TABLE keys; --'` (SQL fragment)
- `kid: 'a' * 10_000` (oversized — would also fall under DoS but not covered)
- `kid: '${process.env.SECRET}'` (template injection placeholder)

**Why SHOULD_FIX, not MUST_FIX**: if W1 implements `JwksCache.getKey(kid)` as a `Map.lookup`, malicious kids cannot reach a filesystem or SQL layer. The blast radius depends entirely on the implementation. But a test that explicitly uses a malicious kid documents the constraint and would catch any regression where someone later tries to "improve" caching with a file backend.

**Recommended hardening**: add one test that throws 4 different malicious `kid` values at the middleware. Each should return 401 with no observable side effect (no thrown unhandled exceptions, no `jwksClient.callCount` more than expected).

#### S5. **Test #48 (JWKS timeout) does not bound response time**

**Where**: `bearer_auth_jwks_cache_test.dart:69-80`. The test injects a 6-second delay and asserts 401, with an outer test timeout of 10s. If W1 has no timeout at all, the test will pass after waiting the full 6s. The constraint is "5s timeout"; the test does not enforce it.

**Recommended hardening**: wrap the call in a `Stopwatch` and assert `stopwatch.elapsed < const Duration(seconds: 6)`. Tighter would be `< 5500ms` to allow some slack for the 5s timeout + dispatch overhead.

### NICE_TO_HAVE (defense-in-depth optionals — do not gate W1 or W2)

- **N1. `aud: null` literal** (W0 flagged item 8). Test #26 covers absence (key removed). JSON `null` value is a different shape; most validators normalise the two but it's worth a dedicated test if the JWT library used is unknown to coerce `null` into "absent". Status: NICE_TO_HAVE — `dart_jsonwebtoken` treats them equivalently.
- **N2. Bearer + malformed cookie** (e.g., `Cookie: __session=` empty, `Cookie: __session=$$$invalid$$$`). The Bearer path should ignore cookie parsing failures entirely. Currently sessionMiddleware silently no-ops on parse failures, so this is fine in practice — but a regression test would document the contract.
- **N3. `iat` equal to `exp`** (zero-second token validity). Edge of leeway — should reject. Not covered.
- **N4. `iat` after `exp`** (malformed but signed correctly). Not covered. Probably caught by `exp` check.
- **N5. Header with extra unknown fields** (e.g., `kty`, `use` echoed in header). Should be ignored. Not covered.
- **N6. Replay defence within `iat` window** (no `jti` and a token replayed within milliseconds). Not in C00 scope (D4 says "stateless, TTL is authority"), so this is not even NICE — it is explicitly out of scope.
- **N7. Pre-warm JWKS at server start** (W0 flagged item 7). The lazy fetch is acceptable; if pre-warm is desired later, that's a separate ticket.

## Additional findings from the audit (not pre-listed)

- **A1. `roles` parsing depth** — Test #9 injects `{'admin': {'role-id-2': 'org-id'}}` for role injection. Test #40 builds `{role_$i: {rid_$i: 'org-id'}}`. The Zitadel claim shape is `{roleName: {roleId: orgId, ...}, ...}` — confirmed against the ticket's reference to `ZitadelJWTPayload.swift:13`. This is correct.
- **A2. Constant-time signature comparison** — Handled by `dart_jsonwebtoken` internally. No custom comparison in test fixtures. APPROVED.
- **A3. CSRF surface** — Bearer is read from `Authorization` header only; never from cookie. Test #41 confirms `?access_token=...` is rejected. No path allows the token via a CSRF-able vector. APPROVED.
- **A4. Test #14 (`exp` absent) uses `buildJwt`, not `buildValidJwt`** — `buildJwt` defaults include `exp`; the override `'exp': null` removes it. The token is signed and otherwise valid. The contrast between `buildJwt` and `buildValidJwt` is meaningful: tests that probe a single field use `buildValidJwt(payloadOverrides: ...)`; tests that probe header/structure use `buildJwt(...)`. The pattern is consistent. APPROVED.
- **A5. Test #36 (kid absent + multi-key)** — orchestrates a TTL bust to force JWKS refetch with two keys, then issues a token with `kid` removed. Solid setup. The assertion is just "401" without checking that no specific key was selected silently. Acceptable.
- **A6. Helper `expectGenericAuthError` forbids 6 oracle phrases** (`expired`, `signature`, `invalid alg`, `kid not found`, `audience`, `issuer`). Strong. Worth adding `nbf`, `not yet valid`, `clock skew`, `crit` for completeness — but the existing list catches the dominant oracle vectors.
- **A7. `dart_jsonwebtoken` is the verifier library** — confirmed via `pubspec.yaml:dependencies` and the helper's `djw.RSAPrivateKey.raw(...)` usage. This library DOES support `none`/algorithm allowlists and is RFC-7519/8725 compliant. The implementer must explicitly pass an allowlist. The tests do not pin the library; W1 could swap it. That's fine — the tests are library-agnostic.
- **A8. Logger spy uses `Logger.root`** — captures all `package:logging` records. Correct mechanism. Constraint #9 is enforceable as long as W1 uses `package:logging`. (`crypto`-library or `dio` internal logs would NOT be captured if they go elsewhere — but they don't log Authorization headers by default.)
- **A9. Test #41 `?access_token=...`** uses a raw `Pipeline().addMiddleware(...).addHandler(...)` rather than the `callBearer` helper. Reason: `callBearer` puts everything in headers; this test must build a custom URL. The test is correct.
- **A10. Test #45 (Lacuna 3) stacks `bearer → session` middlewares** — perfect ordering test. The 401 from `bearer` short-circuits before `session` even runs. APPROVED.
- **A11. No race condition test for JWKS rotation MID-request** — e.g., request A in flight (waiting on JWKS fetch), request B comes in with a new kid that arrived in the rotation. This is implicitly covered by single-flight (Test #47), but not as an explicit race test. NICE_TO_HAVE.
- **A12. Bearer leeway is configurable** (`bearerLeewaySeconds`) — Tests #15 and #19 use the default (30s). No test verifies that overriding the leeway changes behavior. Minor — the default-path test covers the contract. Skip.

## Final recommendation
